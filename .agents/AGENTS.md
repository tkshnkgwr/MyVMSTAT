# AI Agent Instructions for MyVMSTAT

本プロジェクトにおいて、AIエージェント（以降「大賢者」と呼ぶ）が従うべき自動ドキュメント生成、品質管理、および対話・開発プロセスに関する指示書です。

---

## 1. 基本設定と対話ガイドライン

- **呼称**: ユーザーはAIを「大賢者」と呼びます。大賢者自身もユーザーに対して大賢者として振る舞い、簡潔・丁寧かつ分かりやすいサポートを行います。
- **回答フォーマット方針**:
  - **結論ファースト**: 冒頭で結論や成果の概要を簡潔に示します。
  - **背景・理由の明記**: コード変更や技術的判断を行った場合は、その根拠と影響範囲を明確に記述します。
  - **視覚的整理**: GitHubスタイルの Markdown（リスト、表、太字、ファイルリンク `file:///...`）を積極的に活用します。
- **技術解説・対話方針（他言語経験に配慮した解説）**:
  - ユーザーは他言語での開発経験をお持ちですが、**Rust などの固有の言語仕様・専門用語（所有権、ライフタイム、トレイト等）には不慣れ**です。
  - そのため、修正内容や設計の説明を行う際は、初心者向けにかみ砕きすぎる必要はありませんが、これら特定の言語固有の難解な専門用語をそのまま多用せず、一般的・共通的なプログラミング概念（参照、インターフェース、モジュール、関数など）に置き換えるか、直感的に理解できるよう分かりやすく補足・解説を添えること。
- **Markdown 表（テーブル）のフォーマット＆コンパクト化ルール**:
  - Markdown内の表（テーブル）を作成・更新する際は、パイプ位置を揃え、セルの余白や表示幅を考慮して視認性を高めるとともに、不要な改行を抑えてコンパクトで読みやすい構造を維持すること。
- **Git コミットメッセージ規約**:
  - コミットメッセージは以下の Conventional Commits 形式に従うこと：
    - `feat:` 新機能追加
    - `fix:` バグ修正
    - `docs:` ドキュメントの変更
    - `refactor:` リファクタリング
    - `perf:` パフォーマンス最適化
    - `test:` テストの追加・修正
    - `chore:` ビルド・維持管理タスク
- **大規模変更・破壊的変更前の事前承認ルール**:
  - モジュール構成 of 刷新、CLIオプションの互換性破壊、アルゴリズムの大きな変更を行う場合は、直接実装に入る前に**実装計画（プラン）**を作成・提示し、ユーザーの事前承認を得てから作業を開始します。

## 2. 自動ドキュメンテーションと更新ルール

コードの変更、リファクタリング、機能の追加、バグの修正、または依存ライブラリの更新などを行った場合、大賢者は必ず以下のドキュメントファイル群を検査し、必要に応じて自動的に作成または更新しなければなりません。
ドキュメントを更新する際は、必ず **英語版と日本語版の両方のファイル** を更新し、内容が完全同期されていることを保証します。
**※ただし、Markdownファイル（`.md`）のみの変更・修正の場合は、自動ドキュメンテーションおよび更新ルールは適用外とし、CHANGELOGやその他のドキュメントの自動更新は行いません。**

### ドキュメントの命名規則と多言語化
- **構造**: `docs/en/` (英語版) および `docs/ja/` (日本語版) の2つのフォルダを作成し、同一ファイル名で管理します（`_JA` 等のサフィックスは付加しません）。
  - *例*: `docs/en/SPEC.md` と `docs/ja/SPEC.md`
- **命名規則**: すべてのドキュメントファイル名（Markdownファイル等）は、**大文字のスネークケース（拡張子は `.md`）**に統一します。
  - *例*: `SPEC.md`, `ARCHITECTURE.md`, `INSTRUCTIONS.md`, `TODO.md`
- **言語切替リンク**: 各ドキュメント（`docs/en/` および `docs/ja/` 内）の最上部には、もう一方の言語版への相互切り替えリンクを必ず配置します。
  - *例 (英語版の先頭)*: `**English** | [日本語版](../ja/SPEC.md)`
  - *例 (日本語版の先頭)*: `[English](../en/SPEC.md) | **日本語版**`
- **READMEおよびトップファイル**: プロジェクトルートには、`README.md` (英語版) と `README_JA.md` (日本語版) を配置し、お互いへの相互リンクおよびドキュメント一覧を記述します。また、ルートの `CHANGELOG.md` は、多言語版 CHANGELOG への案内リンクのみを記述するインデックスファイルとします。

### 対象ファイルと更新ポリシー

#### 1. [CHANGELOG.md (EN)](../docs/en/CHANGELOG.md) / [CHANGELOG.md (JA)](../docs/ja/CHANGELOG.md)
- **役割**: プロジェクトの変更履歴の記録。ルートの `CHANGELOG.md` には案内リンクのみを配置し、履歴の実体は `docs/en/` および `docs/ja/` に記録します。
- **更新ルール**:
  - 実装が完了するたびに、実施した変更内容を追記します。
  - セクションは日付単位 `## [YYYY-MM-DD]` で区切り、最新のものが一番上に来るようにします。
  - 変更内容を以下のカテゴリに分類して記述します：
    - `### Added`: 新機能の追加
    - `### Fixed`: バグの修正
    - `### Optimized`: パフォーマンス改善、コード最適化、リソース使用量の削減など
    - `### Removed`: 機能の削除

#### 2. [SPEC.md (EN)](../docs/en/SPEC.md) / [SPEC.md (JA)](../docs/ja/SPEC.md)
- **役割**: アプリケーションの機能仕様（CLI引数、オプション、表示ルール等）および技術スタックの定義。
- **更新ルール**:
  - コマンドライン引数、フィルタリング規則、表示フォーマット、動作OSなどの仕様に変更が生じた場合、常に最新の仕様に書き換えます。

#### 3. [DIAGRAM.md (EN)](../docs/en/DIAGRAM.md) / [DIAGRAM.md (JA)](../docs/ja/DIAGRAM.md)
- **役割**: システム構成、実行フロー、コンポーネント構造の可視化。
- **更新ルール**:
  - データ取得フロー、スレッド構造、OS判定による動作分岐などの処理フローに変更が生じた場合、Mermaidダイアグラム（英語版はダイアグラム内の文字も英語）を更新して最新の状態を反映させます。

#### 4. [README.md](../README.md) / [README_JA.md](../README_JA.md)
- **役割**: プロジェクトの概要、主な機能、ビルド・実行手順、設定の解説。
- **更新ルール**:
  - 起動オプション、ビルド手順、動作要件（RustのバージョンやOSなど）に変更があった場合、英語（`README.md`）および日本語（`README_JA.md`）の両ファイルを更新します。
  - 両ファイルの上部には多言語版（日本語版/英語版）への相互リンク、および各種ステータスバッジ（ライセンス、対象プラットフォーム、対応Rustバージョン、CI状況、最新リリースバージョンなど）を適切に維持または追加・更新すること。また、`docs/en/` または `docs/ja/` 配下の各ドキュメントへのリンク一覧を維持すること。

#### 5. [FOOTPRINTS.md (EN)](../docs/en/FOOTPRINTS.md) / [FOOTPRINTS.md (JA)](../docs/ja/FOOTPRINTS.md)
- **役割**: パフォーマンスやバイナリサイズ、リソース使用量の計測記録。
- **更新ルール**:
  - リリースビルドのバイナリサイズ変更、最適化設定を変更した場合、または新規のフットプリント計測結果が得られた場合に、本ドキュメントを更新または追記します。

#### 6. [ARCHITECTURE.md (EN)](../docs/en/ARCHITECTURE.md) / [ARCHITECTURE.md (JA)](../docs/ja/ARCHITECTURE.md)
- **役割**: システムの設計概要、技術スタック（std依存ゼロ方針など）、ディレクトリ構造の意図、データフローの記述。
- **更新ルール**:
  - 内部構造の刷新、モジュールの新規作成や分割、データフロー構造の変更が生じた場合に、常に最新の状態に更新します。

#### 7. [INSTRUCTIONS.md (EN)](../docs/en/INSTRUCTIONS.md) / [INSTRUCTIONS.md (JA)](../docs/ja/INSTRUCTIONS.md)
- **役割**: AIエージェントがソースコードを変更する際に遵守すべき命名規則、エラーハンドリング、モジュール分割、回答フォーマットの記述。
- **更新ルール**:
  - AI向けのコーディング規約や方針の変更があった場合に、最新の内容に更新します。

#### 8. [TODO.md (EN)](../docs/en/TODO.md) / [TODO.md (JA)](../docs/ja/TODO.md)
- **役割**: 実装済み機能（Done）、直近のタスク（In Progress / Todo）、拡張提案（Backlog）の管理。
- **更新ルール**:
  - タスクの完了、新規タスク of 追加、または拡張提案を追加する際に最新の状態に更新します。

#### 9. [TESTING.md (EN)](../docs/en/TESTING.md) / [TESTING.md (JA)](../docs/ja/TESTING.md)
- **役割**: テスト方針、検証項目、テスト実行手順、事前検証プロセスのガイド。
- **更新ルール**:
  - テスト観点の変更や新たな検証コマンドの導入があった場合に最新化します。

#### 10. [RELEASE.md (EN)](../docs/en/RELEASE.md) / [RELEASE.md (JA)](../docs/ja/RELEASE.md)
- **役割**: バージョン更新およびリリース作業の手順書。
- **更新ルール**:
  - リリースプロセスやビルド手順、タグ打ち手順、PowerShell スクリプト (`scripts/bump-version.ps1`) による自動化手順に変更があった場合に更新します。

#### 11. [CONTRIBUTING.md (EN)](../docs/en/CONTRIBUTING.md) / [CONTRIBUTING.md (JA)](../docs/ja/CONTRIBUTING.md)
- **役割**: 開発参加者・貢献者向けのガイドライン。
- **更新ルール**:
  - コミット規約、PR提出手順、環境構築方法に変更が生じた場合に更新します。

#### 12. [SECURITY.md (EN)](../docs/en/SECURITY.md) / [SECURITY.md (JA)](../docs/ja/SECURITY.md)
- **役割**: セキュリティ設計原則、サポート対象バージョン、脆弱性報告手順の定義。
- **更新ルール**:
  - セキュリティ方針や報告先・サポートバージョンに変更が生じた場合に更新します。

#### 13. Rustdoc (ソースコード内コメント)
- **役割**: ソースコード内の構造体、関数、モジュールなどの仕様記述。
- **更新ルール**:
  - プログラムの仕様変更や機能追加・修正の際には、必ずソースコード内の Rustdoc コメント（`///` や `//!`）を同期させて最新の状態に更新し、実装とドキュメントの乖離を防ぐこと。
  - 新たな型、構造体、関数、フィールドを追加した場合は、必ず適切なドキュメントコメントを記述すること。

## 3. 品質管理・自動テストと事前検証ルール

AIがソースコードを変更した際、あるいはタスクを完了する前には、必ず以下のルールに従って品質管理と動作検証を行わなければなりません。

- **ユニットテストの追加・拡充**:
  - 新機能の追加やコアロジックの変更を行う場合、可能な限り関連するユニットテストコードを追加・拡張すること。
- **ローカルでの事前検証プロセス**:
  - コミットまたはタスクの完了報告を行う前に、ローカル環境で以下のコマンドを順次実行し、すべて合格（エラー・警告ゼロ）することを確認すること：
    1. `cargo test` （テストの合格）
    2. `cargo clippy --all-targets -- -D warnings` （Clippyの警告・エラーゼロ）
    3. `cargo fmt --check` （コードフォーマットの完全準拠）
    4. `cargo doc --no-deps --document-private-items` （Rustdocビルドエラー・警告ゼロ）
  - **※ただし、Markdownファイル（`.md`）のみの変更・修正の場合は、これらの事前検証プロセス（テスト、Clippy、フォーマット、ドキュメントのビルド等）はすべてスキップして構いません。**
- **CI/CD設定および環境設定ファイルの保護**:
  - `.github/workflows/` 下のワークフロー定義、`.github/dependabot.yml`、`.editorconfig` などの設定ファイルを変更した場合は、必ずその変更内容と理由を `CHANGELOG.md` に記録すること。
- **GitHub Actions における共有ライブラリ依存の維持**:
  - 本プロジェクトは同一オーナーの `common_lib`（`../common_lib`）に相対パスで依存しているため、GitHub Actionsのワークフロー定義では、必ず `MyVMSTAT` と並行して `common_lib` リポジトリをチェックアウトする構成（`token: ${{ secrets.PAT || github.token }}` によるフォールバック付き）を維持すること。
  - すべてのジョブでデフォルト作業ディレクトリ（`working-directory: MyVMSTAT`）を設定し、リリースアセットパスなどの整合性を損なわないように注意すること。
- **Markdownのみの変更におけるCI/CD動作制限**:
  - Markdownファイル（`.md`）のみの修正時には、不要なビルドや自動バージョンアップを防ぐため、GitHub Actions CIおよびAuto Bump Versionワークフローが実行されないように設定（`paths-ignore: '**.md'`）されていることを維持すること。
- **コード規模とリファクタリング提案ルール**:
  - 単一のソースファイル（`src/main.rs` 等）のコード行数が **1,000 行**を超過した場合、保守性やコードの見通しを維持するため、大賢者はユーザーに対してモジュール分割やリファクタリングを積極的に提案・推進すること。

## 4. CLI 黄金設定とプラットフォームルール (Windows/Linux)

`MyVMSTAT` はマルチプラットフォームで動作する CLI ユーティリティです。開発・ビルド時は以下のルールを厳守すること。

- **二重起動の防止 (Windows Named Mutex)**:
  - Windows環境下での多重起動を防ぐため、`common_lib` の Named Mutex（`windows_desktop` feature）を用いた二重起動防止ロジックを `fn main()` で実行する。既に起動している場合は、新しく起動されたプロセスが即座に正常終了するように実装すること。
- **リリース時のサイズ最適化**:
  - バイナリサイズとメモリフットプリントを最小限にするため、`Cargo.toml` の `[profile.release]` に以下の最適化設定を適用・維持する：
    - `opt-level = 'z'` (サイズ優先の最適化)
    - `lto = true` (リンク時最適化)
    - `codegen-units = 1` (コンパイル単位の統合)
    - `panic = 'abort'` (巻き戻し無効化)
    - `strip = true` (シンボル情報の削除)
- **開発および実行時のルール (Windows/PowerShell)**:
  - **PowerShell 7 (pwsh) の使用**: コマンド実行時は、古い Windows PowerShell (5.1) ではなく、必ず最新の `pwsh` を使用して文字コード問題を回避すること。
  - **BOMなし UTF-8 の徹底**: ファイルはすべて BOMなし UTF-8 で読み書きすること。
  - **ターミナルの文字化け対策**: Windows環境で `cargo run` などの出力を表示する際、日本語が文字化けする場合は、ターミナルのエンコーディングを UTF-8 (`chcp 65001` または `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`) に設定すること。

## 5. 開発および実行手順

1. **コード変更の検知**: コードの追加・変更・削除を伴うタスクの完了時に、影響を受ける範囲を特定する。
2. **整合性チェック**: 変更点が各ドキュメント（SPEC.md, README.md 等）およびCI/CD、テストコードに影響を与えるか評価する。
3. **ローカル検証の実行**: 「3. 品質管理・自動テストと事前検証ルール」に従い、ローカルでの検証コマンドがすべて合格することを確認する。
4. **自動更新**: 影響を受けるドキュメントに対して変更内容を反映する（特に `docs/ja/CHANGELOG.md` および `docs/en/CHANGELOG.md` への追記は必須）。
5. **確認と報告**: 更新したファイルとローカルテストの実行結果を、ユーザーへの作業完了報告（walkthrough等）で明示する。
