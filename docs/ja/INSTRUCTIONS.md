# AI・開発者向けコーディングスタイル規約: INSTRUCTIONS

本ドキュメントは、**MyVMSTAT** プロジェクトにおいて今後ソースコードの修正・機能追加を行う際、開発者およびAIアシスタントが遵守すべきコーディングスタイル、エラーハンドリング方針、コンポーネント設計、および出力フォーマットについて規定します。

---

## 1. 命名規則

Rust の標準的なネーミングコンベンション（RFC 430）に準拠します。

| 対象項目 | 表記法 (Casing) | 具体例 | 備考 |
| :--- | :--- | :--- | :--- |
| **変数 / 関数 / パラメータ** | `lower_snake_case` | `delay`, `parse_args`, `loop_count` | 簡潔で分かりやすい名称を選択する |
| **構造体 / 列挙型 / トレイト** | `PascalCase` | `VmstatData`, `TelemetryProvider` | 略称は全て大文字にする (例: `CliAction`) |
| **定数 / マクロ** | `UPPER_SNAKE_CASE` | `CARGO_PKG_NAME`, `Local\MyVMSTAT-...` | 視認性を高めるために大文字統一 |
| **ソースファイル名** | `lower_snake_case` | `main.rs` | モジュール名と一致させる |
| **ドキュメントファイル名** | `UPPER_SNAKE_CASE.md` | `ARCHITECTURE.md`, `TODO.md` | 本プロジェクト独自の統一ルール |

## 2. エラーハンドリングの方針

安全でクラッシュしないCLIユーティリティを構築するため、堅牢なエラーハンドリングを実施します。

- **例外（パニック）の回避**:
  - `unwrap()` や `expect()` の使用は、テストコード、または「絶対に失敗しないことが保証されている極めて限定的な文脈」を除き、原則禁止します。
  - パース処理（文字列から数値への変換など）で失敗する可能性がある場合は、`parse().unwrap_or(0)` などの安全なフォールバック値を適用するか、`Result` を呼び出し元へ返します。
- **Result/Option を用いた戻り値での伝搬**:
  - コマンドライン引数のパースなど、ユーザー入力に起因するエラーは `Result<T, String>` などの戻り値として表現し、メイン関数で受け取って処理します。
- **致命的エラー時のプロセス終了**:
  - 二重起動の検知（ミューテックスの取得失敗）や、不正なコマンドライン引数が指定された場合など、継続が不可能な致命的エラーが発生した場合は、エラーメッセージを標準エラー出力（`eprintln!`）に書き出し、`std::process::exit(1)` によって終了コード `1` で速やかに終了させます。

## 3. コンポーネントおよびモジュールの分割基準

- **単一ファイルの維持と1,000行基準**:
  - 本ツールはシステム情報を取得し、整形して一行ずつ出力するというシンプルな責任を持っています。
  - 単一ソースファイル（`src/main.rs`）の行数が **1,000 行を超えた場合**、コードの見通しと保守性を確保するため、機能・モジュール単位（例: `src/provider.rs`, `src/cli.rs` 等）への分割やリファクタリングの実施・提案を推進します。
  - 1,000 行未満の規模である場合は、ファイル分割による過度な複雑化を防ぐべく、`src/main.rs` の単一ファイル構造を維持します。
- **外部共通クレートへの切り出し (`common_lib`)**:
  - Windows API を直接叩く Named Mutex による二重起動防止のような、「他のデスクトップアプリでも再利用可能なプラットフォーム固有の機能」は、本プロジェクト内ではなく、共通ライブラリ `common_lib` に実装し、依存関係としてインポートします。

## 4. AIアシスタント出力フォーマットおよび挙動指定

AIアシスタントが本プロジェクトで作業を行う際は、以下のルールを厳守してください。

- **最小限の解説**:
  - コード修正案や実装コードを提案する際、冗長な解説文や挨拶は省き、実行可能なコードブロックまたは `diff` ブロックを主体として簡潔に出力してください。
- **ドキュメントの自動更新**:
  - ソースコードに変更を加えた場合は、作業完了前に必ず開発ガイドライン（`.agents/AGENTS.md`）の「6. ドキュメント自動更新ルール」に従い、`CHANGELOG.md` や関連する Markdown ドキュメント（`SPEC.md`, `ARCHITECTURE.md`, `TODO.md`）を自動的に更新してください。
- **テストの実行**:
  - 変更を行った後は、必ず `cargo test` を実行して、既存の自動テストケースがすべて正常にパスすることを確認してください。
- **相対パスリンクの徹底**:
  - リポジトリ内のドキュメント同士をリンクする際は、ポータビリティ維持のため、絶対にローカル環境の絶対パス（`file:///`）を使用せず、相対パス（例: `docs/SPEC.md`）を用いてリンクを記述してください。
